# Dataset Card for Synthetic Multi-Turn Customer Support Tickets (Consumer Electronics)

100 wholly synthetic multi-turn customer-support conversations in a consumer-electronics domain,
each with assigned ticket metadata, a machine coherence score, and provenance linking it to the
run that produced it.

## Dataset Details

### Dataset Description

Every conversation is fabricated by a language model from a committed domain prompt. No real
support transcript, customer, or agent is involved at any point, and none was used as source
material. The dataset exists to support work that needs support-ticket-shaped text — dialogue
modelling, routing and triage experiments, evaluation harnesses — without the privacy exposure
that real support archives carry.

Each record is one complete ticket: an ordered sequence of turns alternating customer and agent,
starting with the customer, plus the metadata the conversation was generated to fit.

Composition is **assigned before generation rather than measured after it**. Each record's
category, priority, channel, resolution status, turn count, subdomain and timestamps are seeded
choices made from the run seed and the record's position, so the distribution is a property of the
request rather than an accident of what the model happened to produce.

## Uses

### Direct Use

Suitable for:

- fine-tuning or evaluating multi-turn dialogue models on support-style exchanges;
- developing ticket classification, routing, or summarisation components where metadata is known
  by construction rather than inferred;
- testing data pipelines that consume conversational JSONL, since every record is schema-validated
  and carries stable identifiers;
- teaching and demonstration, where a real support archive would be inappropriate to distribute.

At 100 records this corpus is best treated as a **pilot**: large enough to exercise a pipeline
end to end, too small to train on or to draw distributional conclusions from.

### Out-of-Scope Use

- **Not a sample of real support traffic.** Nothing here was observed. Frequencies, phrasing, and
  problem distributions reflect a prompt and a model, not any real customer population. Do not use
  it to estimate how often anything happens in the world.
- **Not a benchmark.** The coherence scores are machine-generated by the same model family that
  wrote the conversations, and the one calibration performed found the judge's ranking did not
  track a human reviewer's (see Limitations). Treat the scores as a filtering artifact, not ground
  truth.
- **Not a privacy-safe stand-in for de-identification research.** Synthetic-by-construction is not
  the same problem as de-identified-after-the-fact, and this dataset cannot be used to validate a
  de-identification method.
- Not suitable for training a system to make consequential decisions about real people.

## Dataset Structure

One JSON object per line (JSONL, UTF-8). 100 records, 213,446 bytes. A single `train` split; no
test split is provided, because at this size any split would be too small to be meaningful.

| Field | Type | Notes |
|---|---|---|
| `record_id` | string (UUIDv5) | Stable, derived from the run and position |
| `record_index` | int | Position in the run, ascending, 0–99 |
| `run_id` | string (UUID) | The generation run; matches the manifest |
| `schema_version` | string | `1.0.0` |
| `source_id` | string | Domain prompt identity: `name@sha256[:12]` |
| `subdomain` | string | Seeded choice from the prompt's declared list |
| `scenario` | string | The specific situation the model elaborated |
| `metadata` | object | `category`, `priority`, `channel`, `resolution_status`, `created_at`, `resolved_at` |
| `turns` | array | `{role: "customer"｜"agent", content: string}`, customer first, strictly alternating |
| `quality` | object | `coherence_score` (0–1), `rubric_id` |
| `generation` | object | `model_id`, `judge_model_id` |

`resolved_at` is present when and only when `resolution_status` is `resolved`.

**Achieved composition** (identical to requested — worst-member drift 0.00pp):

| Dimension | Distribution |
|---|---|
| category | billing 50%, technical 50% |
| priority | normal 100% |
| channel | chat 50%, email 50% |
| resolution_status | resolved 75%, escalated 25% |

Turn counts range 4–8. 19 of the domain's 20 declared subdomains appear.

## Dataset Creation

### Curation Rationale

Real support tickets are among the densest sources of personal data that exist, which makes them
both valuable and largely undistributable. Scrubbing them after the fact is unreliable and
irreversible once published. This dataset takes the other route: admit no real identifiers at any
point, so there is nothing to scrub.

The generator is the deliverable; this corpus is one output of it. The pipeline enforces
reproducibility, provenance, and a blocking privacy scan as structural properties rather than
review-time checks.

### Source Data

#### Data Collection and Processing

Generated by `ollama_chat/gpt-oss:20b`, self-hosted, from a committed domain prompt document
(`consumer-electronics-support.md@8d67eaf56b0a`) declaring 20 subdomains.

Per record: the pipeline assigns metadata from the seed, prompts the model for a conversation
fitting that assignment, then applies four gates in order — structural validation, a blocking
privacy scan, coherence judging, and schema validation. A record failing any gate is discarded and
counted by reason; the slot is retried up to three times. Output is written to staging and moved
to the release path only after the privacy floor is demonstrated against known canaries.

**This run:** 106 generated, 100 written. Discards: 3 `coherence_below_threshold`, 2
`turn_count_out_of_range`, 1 `structural_invalid`. Zero duplicates, zero privacy blocks.

Reproduction inputs: run `4fa1f060-3786-4cf1-9e11-8eb791c4ccd5`, seed `7`, code revision
`5f4ffd45ecce` (clean tree), corpus SHA-256 `cc23ff33a1e74e9edb294425…`.

Reproduction is **structural, not textual**. Given the same seed, config, prompt and rubric, every
record lands on the same composition, subdomain, turn count and timestamps — but no model sampling
seed was set, so the conversation text differs on every run. This is stated as a limitation of the
method, not a defect of the run.

#### Who are the source data producers?

A language model, prompted by an automated pipeline. No humans produced any conversational
content, and no human-authored text was used as source material.

### Annotations [optional]

#### Annotation process

Each conversation is scored 0–1 for coherence by a second model call against a committed, versioned
rubric (`coherence-v2`) with four weighted criteria: `single_issue` (0.30), `role_consistency`
(0.25), `conversational_flow` (0.25), `metadata_fit` (0.20). The record's score is the weighted
mean. Records below 0.8 are discarded before release; the score of every surviving record is
retained.

Score distribution: mean 0.973, median 1.0, min 0.825, max 1.0. By bucket — 0.80–0.85: 2,
0.85–0.90: 4, 0.90–0.95: 16, 0.95–1.00: 78.

#### Who are the annotators?

`ollama_chat/gpt-oss:20b` — **the same model that generated the conversations.** See Limitations.

A single human calibration was performed against a 20-record random sample (seed 5) by `arpieb`,
recorded at `calibration/coherence-v2.calibration.json`.

#### Personal and Sensitive Information

The dataset contains no real personal data by construction. Identifier-shaped values are drawn
from ranges reserved for fiction — RFC 2606 domains (`example.com`, `.test`, `.invalid`), NANP
`555-0100`–`555-0199` phone numbers, published payment-card test numbers — so they cannot refer to
anyone.

Every record was scanned before admission: 103 records, 733 fields, 76 findings, **all exempt by
reserved range, zero blocking**. No privacy exception has ever been approved for this project;
`privacy/exceptions.json` does not exist.

The scan does not detect: non-US government identifiers, postal codes, full postal addresses, IBAN
bank account numbers, or person names. These are declared gaps, restated here so a clean scan is
not mistaken for coverage it does not provide. Person names in particular are present throughout
and are fabricated.

## Bias, Risks, and Limitations

**The judge shares a model with the generator.** The same `gpt-oss:20b` wrote and scored every
conversation. A model evaluating its own output is a known source of inflated agreement, and 78%
of records scoring above 0.95 should be read in that light.

**Calibration found a ranking disagreement, not merely leniency.** In the one human calibration
performed (n=20), gate agreement was 100% — but that is an artifact: the reviewer's lowest score
was exactly the 0.8 threshold, so nothing was rejected by either side. Rank correlation was
**−0.07**, effectively zero. The crosstab is the finding: all five conversations the reviewer rated
lowest received a perfect 1.0 from the judge. A uniformly generous judge that orders correctly can
be fixed by moving the threshold; this one cannot. The coherence scores should not be relied on to
rank quality within this corpus. n=20 with three distinct human values is enough to raise the
concern and not enough to characterise it.

**No priority variation.** Every record is `priority: normal`, because the run requested that
distribution. The field is present and constant, and is useless as a training signal here.

**Single domain, single model, single run.** One consumer-electronics prompt, one 20B model, one
seed. Phrasing, product names, and problem framing will be markedly less varied than real traffic,
and stylistic tics of one model will run through the whole corpus.

**Small.** 100 records. Any distributional claim drawn from it is unreliable.

**Fabricated products and companies.** Product names appearing in conversations are invented. Any
resemblance to real products is incidental and not an endorsement or a description.

### Recommendations

Users should be made aware of the risks, biases and limitations of the dataset. Specifically: do
not use `coherence_score` to rank or filter within this corpus without independent validation; do
not treat the composition as descriptive of real support traffic; and do not train on 100 records
and expect generalisation. If you need a corpus large enough to train on, regenerate at scale from
the repository rather than resampling this one.

## Glossary [optional]

- **Slot** — one unit of generation work. Its metadata is assigned before any model call, which is
  what makes the composition exact and lets a discarded record be retried without changing the
  corpus shape.
- **Subdomain** — a category declared by the domain prompt document (e.g.
  `billing-invoice-discrepancy`). Chosen by seed before dispatch; the model elaborates a specific
  scenario within it.
- **Exempt by range** — a privacy finding whose value comes from a range a standard reserves for
  fiction. Reported rather than hidden, so the scan never looks cleaner than it was.
- **Structural reproduction** — same seeded choices at every position, different conversation text.
  What this pipeline guarantees, given no model sampling seed.
